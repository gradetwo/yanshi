# 开发 skill：性能与资源

> 何时用：**写任何"会被反复调用/随规模增长"的代码时**（提交、渲染、折叠、序列化、轮询……），
> 以及排查"越用越慢 / CPU 打满 / 内存涨"时。不是"专门做优化任务"才用 ✓。

## 一条主线

**先量 → 归因到大头 → 只优化大头（小投入大回报）→ 用能红的判据锁住 → 复测（含负对照）。**

顺序不能换 ✓。跳过"量"直接改代码，本仓库已实证会**白干一轮**（见"反模式 ①"）。

## 一、量什么（三个都要看，不能只看墙上时间）

| 维度 | 怎么量 | 为什么要 |
|---|---|---|
| **响应耗时** | 分阶段计时：入口 → 折叠/计算 → 渲染 → 落盘/回复 ✓ | 只看总时长无法定位 |
| **CPU** | 进程 CPU%（`top`/`pidstat`）✓；是否**单核打满** | 单核 100% ⇒ 串行热点；多核则另有瓶颈 |
| **内存** | 峰值 RSS ✓；**缓存是否随版本无限增长**（如按 seq 缓存的快照 ✗） | O(N²) 内存比慢更致命 |

**规模变量要选对 ✓**：对象数、原子数、图层数、像素数、tile 数、批次大小是**不同的量** ✓，
一条曲线只能说明它与**那一个**变量成比例 ✓。要分清"随对象数增长"与"随画布尺寸增长" ✓。

## 二、归因：统计出大头，而不是猜

1. **并排报数**（最高性价比 ✓）：把候选量**在同一段代码里一起打出来** ✓（如 `natural` / `resized` / `zoom` ✓）。
   两个数一比，往往一眼定案 ✓ —— 本条在本仓库已多次一次定案 ✓。
2. **计数**：给可疑调用计数（每次提交调了几次）✓ —— 比读代码猜可靠 ✓。
3. **确认热点被走到** ✓：判定"是它"之前，先加一行日志/计数**证明这条路径被执行** ✗
   —— 本仓库实证：找到一处真实的 O(N)，但它**不在被测路径上** ⇒ 改了零效果 ✓。
4. **算式闭合**：把"误差"换算到**另一个坐标系**再解读 ✓
   （如 7 文档像素 ＝ 5.2 客户端像素 ⇒ 立刻排除"取整"这一整类 ✓）。
5. **分阶段**：整幅 vs 区域、冷启动 vs 稳态、首次 vs 后续，分开量 ✓。

## 三、只优化大头（小投入大回报）

- **优先**：代价**与规模成比例**、且在**热路径**上、且修法**局部**的那一项 ✓。
- **次序**：先把"整幅/全量"改成"只做变更部分"（通常一个量级 ✓），**再**谈并行（通常 3~5× ✓）。
- **别急着删**：当某段代码"看起来多余"✗，先确认它是否**被别人依赖为契约** ✓（见反模式 ②）。
- **优先改粒度，不改有无** ✓：本仓库的实证修法是"整幅缩略图 ⇒ 只刷新变更块" ✓，
  而不是"删掉这次渲染" ✗ —— 后者破契约、前者**既快又对** ✓。

## 四、判据（硬要求）

- 判据**必须能红** ✓，且**变异要改到被判条件本身** ✓（不是改日志措辞 ✓）。
- 语义优先于计时 ✓：计时在共享机器上会抖 ✗ ⇒ 优先断言**语义量**
  （如"失效范围是脏区而不是整层" ✓、"每次提交的全幅渲染次数 1 → 0" ✓）。
- 计时判据要做**前后对照** ＋ **负对照**（未优化的路径不许变差 ✓）。
- 门禁（fmt / clippy / test）**必须全绿**；**不留红树** ✓。

## 五、反模式（都来自本仓库的实证）

| # | 反模式 | 后果 | 正确做法 |
|---|---|---|---|
| ① | 找到"某处 O(N)"就动手 ✗ | 改了零效果（它不在被测路径） | 先加**计数/日志证明**它在热路径 ✓ |
| ② | "顺手解耦/删掉看起来多余的调用" ✗ | 破既有契约，2 条测试红 | 先查该函数**被哪些测试断言** ✓；**先回退**再想 ✓ |
| ③ | 用**注释**判断行为 ✗ | 注释常描述**历史**而非现状 | 读**实现**与**断言** ✓ |
| ④ | 只看总时长 ✗ | 分不清 CPU / IO / 内存 | 同时看耗时、CPU%、峰值 RSS ✓ |
| ⑤ | 临时诊断只 `print` 不落盘 ✗ | CI/runner 只回显头尾 ⇒ **看不到** | **落盘** ✓，定案后**移除** ✓ |
| ⑥ | 一个症状只归一个因 ✗ | 修好一个、另一个还在 | **分别定责** ✓（如 rect 漂移 1.5px vs viewport 变化 49px ✓） |
| ⑦ | 误差不换坐标系就下结论 ✗ | 误判为"取整" | 换算到另一坐标系再解读 ✓ |
| ⑧ | 把"值是 0"当成"被赋成 0" ✗ | 追错方向整轮 | 它可能是**钳制/派生**的结果 ✓（`docW - viewW = 0` ✓） |

## 六、完整例子（本仓库 4K 单笔 O(N)）

```
现象 ✓：4K 下单笔 1.5s~4.0s、单核 100%、随作品笔数线性变慢（600 笔时单笔 ~40s）✓
量   ✓：debug 4K，第 1 笔 15.2s → 第 32 笔 28.8s（+452ms/笔）✓；小区域 render_region **平** ✓
归因 ✓：并排报数 ＋ 读实现 ⇒ `run_pending_jobs` 每提交调 `render_document_preview` ✗，
        而它为了一张 256² 小图**先做整幅全分辨率渲染**（830 万像素）✗ ⇒ O(全部对象) ✓
反模式 ②：试着"删掉这次渲染" ✗ ⇒ 两条契约测试红 ⇒ **回退** ✓
修法 ✓：**改粒度** —— 缓存缩略图像素 ＋ 只渲染脏区 ＋ 只刷新对应块 ✓
判据 ✓：`an_exact_bitmap_import_only_invalidates_its_own_region`（变异可红 ✓）
复测 ✓：第 1 笔 16.2s → 第 32 笔 15.1s（斜率 ≈ 0 ✓，第 32 笔快 ~48% ✓）
```

## 七、动手前的检查清单

- [ ] 三个维度都量了（耗时 / CPU / 内存），规模变量选对了 ✓
- [ ] 大头**有证据**（计数 / 分阶段 / 并排报数），且证明**这条路径会被走到** ✓
- [ ] 修法是**改粒度**而非**改有无**；契约测试先查过 ✓
- [ ] 判据能红、变异打到被判条件本身 ✓；门禁全绿 ✓
- [ ] 复测含**前后对照**与**负对照**；临时诊断已清理 ✓

## 八、依赖与库的取舍

1. 本仓库**不设**"只允许某个依赖"的规则。旧规则已取消。
2. 判据是**收益与代价**。收益远大于代价就采用成熟、稳定、高质量的库。
3. 报告与提交必须写明两面：好处与代价。缺一面不算完成。
4. 旧规则若挡住高收益方案，第一动作是**提出修改**，不是默认遵守。
5. 核对因素：收益量级、体积、确定性、平台支持、供应链、构建时间、维护状态。
6. 例子（本仓库实测）：
   - 手写 deflate 的存在原因是旧规则。它的性能上限因此被压低。
   - 瓦片并行的收益是全幅渲染 122 秒的量级。它远大于 PNG 编码 1.7 秒。
   - 因此先做并行，不是先换压缩库。先挑回报最大处，再谈投入。

## 九、判据的可验证性（第 1126-1129 轮沉淀，全部有实测支撑）

### 9.1 判据必须能**脱离 runner 单独跑**
**事实**：判据 runner 把仓库**复制到它自己的 `$ROOT_DIR`** 再跑。
**后果**：在仓库工作树里做变异，runner 读到的仍是副本 ⇒ **变异不会让 runner 变红** ✗。
**实测**：同一份判据，**直接跑**时基线绿、变异红；**经 runner 跑**时变异前后都绿。
**要求**：
1. 判据用**自身位置**解析仓库根（`import.meta.url` / `CARGO_MANIFEST_DIR`），
   **不要**依赖 cwd 的相对路径。
2. 变异验证一律在**直接跑**的路径上做；runner 只用来确认"隔离环境里也绿"。
3. runner 的 `RUN EXIT=0` **不能**作为"该判据能红"的证据。

### 9.2 观测前先**断言对象身份**（本会话六次同族错误的统一对策）
症状：判据红了，第一反应是"产品坏了"。
**实际多数是量错了对象**。本会话实例：读错文档（用错 zip）、跨分辨率比体积（256² vs 4K）、
把 runner 的**回显截断**当成内容缺失、按缩进 grep 只匹配到无关项、浏览器执行的是**旧 Service Worker 缓存的旧 JS**、
**`window.yanshi.state` 是函数**却去读它的属性（于是 `tool` 永远是 `null`，据此推出三个错误结论）。
**要求**：观测前先打印并断言：`typeof`、`Object.keys`、元素 `id`、画布 `width/height`、
上下文类型（`getContext("2d"/"webgl")`）、以及"服务端实际发出的资产是否含我改的那段"。

### 9.3 "只加一个**只读**探针，判据就变绿" ⇒ 强信号：**时序**
只读探针唯一的作用是**引入延迟**。它一变绿，就说明**等待条件与断言条件不一致**，
而不是产品好了。修法：把固定 `sleep` 换成**有界轮询到断言条件成立**。
反过来：如果轮询很久（例如 20 秒）仍是老读数，那就是**真的没发生**，不是时序。

### 9.4 "判据红，而**我自己的日志一行都没出现**" ⇒ 怀疑**致命错误**
本会话两次：① `const` 助手的**暂时性死区**（定义在调用点之后）；② 用正则**全局**替换采样点，
把助手**内部**那次采样也换了 ⇒ **自递归**。都用"改成函数声明 / 只替换外部调用"修掉。

### 9.5 合成事件的三个陷阱（浏览器判据）
1. **绘制画布是 `#board`**：页面有多个 canvas（overlay、dab），`querySelector("canvas")` 会读错。
2. **`aria-pressed` 可能不反映激活态**：本仓库实测它一直是 `"false"`，别拿它当"工具已选中"的证据。
3. **`spaceHeld`**：`wantsPanEvent = button===1 || tool==="pan" || spaceHeld`。
   只要 `spaceHeld` 为真，落笔处理器**第一行就返回**，事件被平移处理器吃掉
   （现象：`points` 不增长、`dragging` 不变）。判据派发前应先发 `keyup(Space)`，
   并在派发后**断言 `points` 从 0 增长**，而不是只看像素。

### 9.6 环境前提（否则误报）
1. **新 worktree 没有 `crates/yanshi-wasm/pkg`**（gitignore 的构建产物）。
   缺了它 viewer 会**静默退回服务端渲染**，浏览器判据会误报失败。
2. viewer 的 JS/CSS 是 `include_str!` **编进二进制**的 ⇒ 跑浏览器判据前必须
   `cargo build --workspace --bins`（runner **不构建**）。
3. 本机内存小（约 3.8 GB）⇒ 避免并发跑重负载浏览器判据，否则会出现
   `Runtime.evaluate` 超时之类的**非断言类**中断。

### 9.7 已知红名单的进出纪律
**不得凭一次通过就移出**。至少**连跑三次**都通过才移出（本会话因一次通过就移出而犯过错）。
判据**持续红**（每次跑都红）与**时红时绿**要分开：前者先当成真问题登记，后者先查环境与竞态。

### 9.8 转述目标项之前，先查证它的**现状**
本会话三次把"已完成"当成"未做"：
1. `(B)③` `target_installed` 三态 —— 实现早已完成（只缺判据）。
2. `(B)①` 示例覆盖 —— 我以为"57 条"，实际早已 138/141（现 141/141）。
3. `(A)⑤` 服务端渲染显式开关 —— 复选框、localStorage 键、UI 与存储连通**全都在**。
**代价**：浪费轮次，而且进度报告**双向失真**（既少报已完成，也误导优先级）。
**要求**：任何"未做/待做"的判断，都要先有**一条当前代码或当前读数的证据**，
不能凭上一轮的转述或记忆。判断"已完成"同样要给证据（文件 + 行号，或一次实测读数）。

### 9.9 门禁要分两步：先 build，再 test（否则 doc-test 会偶发 E0460）
**现象**：`cargo test --workspace` 间歇性报
`error[E0460]: found possibly newer version of crate 'yanshi_server' which 'yanshi_mcp' depends on`，
指向某个 doc-test；**单独**跑 `cargo test -p <crate> --doc` 却永远是绿的。
**原因**：`cargo test --workspace` 会**一边编译一边跑 doc-test**（doc-test 由 rustdoc 驱动）。
当 rustdoc 看到同一个 crate hash 的 `.rmeta` 与 `.rlib` 同时存在时，就判定"可能有更新版本" ⇒ E0460。
**这不是偶发，也不是资源竞争，更不是判据或产品的问题。**
**做法**：门禁分两步 —— 先 `cargo build --workspace --all-targets`（让编译彻底完成），
再 `cargo test --workspace`。
**已实测确认有效**（第 1161 轮，用 `cargo clean -p yanshi-server -p yanshi-mcp` 制造编译交错）：
直接 test ⇒ E0460 出现 **2 次**；两步 ⇒ E0460 出现 **0 次**。
**⚠️ 另一个陷阱**：两步之后 `cargo test --workspace` 仍可能 EXIT=101，但失败的可能是**另一条**判据。
**EXIT 非零不等于修法无效** —— 必须看**失败的是哪一组**。我第 1157 轮就因此把「修法有效并暴露了另一条红」误判成「修法不生效」。
**教训**：**"重跑就绿"不等于偶发**。遇到间歇性失败，必须抓到失败**全文**再定性；
否则会把确定性问题当成噪声，让"门禁全绿"这句话贬值。

### 9.10 多个 worktree 并行时，必须用独立 target 目录（否则门禁会跑到别人的代码）
**现象**：某条判据在**全量测试**里稳定红，**单独跑**却绿；`cargo build` 之后仍然红；
改动源码也不影响读数。
**原因**：另一个 worktree 的子代理**没有自己的 `target/`**，用主干的 target 做构建。
两个 worktree 的 cargo 单元 hash 与 `extra-filename` 可能相同 ⇒ 产出**同名**测试二进制；
若主干源码文件的 mtime 比那次构建更旧，cargo 会判定"无需重编"，
于是**主干门禁跑的是别人源码编译出来的二进制**。
**实测证据（本仓库）**：主干 target 里那个 `tile_parallel-…` 二进制含字符串 `missed_bytes`，
而主干 `render.rs` 里该字符串出现 0 次、另一个 worktree 的 `render.rs` 里出现 4 次。
**做法**：
1. 每个 worktree 设 `CARGO_TARGET_DIR="$PWD/target"`；
2. 我自己的门禁统一用**独立 target**（如 `CARGO_TARGET_DIR=/tmp/yanshi-gate-target`）；
3. 遇到"全量红、单跑绿"，**第一嫌疑是构建产物污染**，先 `cargo clean -p <crate>` 或换 target 复验，
   再怀疑产品缺陷或判据；
4. **不要**因为这种读数去改产品代码 —— 本会话我差点因此把一处本来正确的共享缓存改成"修复版"。

### 9.11 浏览器离线判据：CDP 的离线模拟到不了 service worker 的 fetch
**现象**：`Network.emulateNetworkConditions {offline:true}` 之后，页面的 `navigator.onLine === false`，
但 service worker 里自己的 `fetch("/mediums/marker.wasm")` **仍然返回 200**。
在 SW 的 debug target 上也设 offline **没有变化**；`Network.setCacheDisabled` 与
`Network.clearBrowserCache` **也没用**（不可变响应照样被 SW 的 fetch 拿到）。
**后果**：任何"只模拟网络条件"的浏览器离线判据，都可能在**被测代码已经坏掉**的情况下**假绿**。
**做法**：
1. 在 SW 上下文里 **stub `self.fetch`**（让它按你的需要在"在线/离线"之间切换）；
2. 加一条**负对照**：一个**故意不缓存**的同源资产在"离线"时**必须取不到**；
   若它仍然返回自己的字节，则判据应当**自宣无效**，而不是通过；
3. 把上面两条写进判据的注释，说明它证明了什么、没证明什么（例如不证明浏览器配额/驱逐）。

### 9.12 回退必须是“带修订号”的（`git add -A` 之后尤其）
**事故**：我在一条命令里先 `git add -A`（把带 `// MUTATION` 标记的判据暂存了），
再 `git checkout -- <path>` 想回退 —— 但**路径式 checkout 只还原工作树、不动索引** ✗
⇒ `git commit` 提交的是**索引里的坏版本** ⇒ 一个带变异标记、断言条件被清空的判据被推送到 main。

**规则**：
1. 只要跑过 `git add -A`，回退就**必须**用 `git checkout <rev> -- <path>`
   （工作树与索引同时还原），或 `git restore --staged --worktree <path>`；
   光写 `git checkout -- <path>` **不算回退**。
2. 提交前核验三件事：① `git status --porcelain` 为空；
   ② 被判文件里 `grep -c MUTATION` 为 0（以及其它故意植入的标记）；
   ③ 与目标版本 `diff` 为空。
3. `git status --porcelain` 的两列含义：**第一列＝已暂存**，第二列＝工作树。
   把两列读混，就会在“已暂存坏版本”时误判为“只是工作树有改动”。
4. 推送后抽样复核**远端**内容（`git show origin/main:<path>`），别只信本地。

### 9.13 读一个工具的行为，必须一路读到**入口**
**实例**（2026-10-06，`new_document` 忽略 `width`/`height`）：
- 只读工具函数 `write_new_document`，会得出"它用了 `document_mut`（按需创建）⇒ 新 id 也走'已存在'分支"的结论。
  **这是错的**：`document_mut` 只是 `get_mut().ok_or(ReferenceNotFound)`，**不创建**。
- **真正的原因在入口**：MCP 的 `tools_call` 在分发**任何**工具前，无条件用 CLI 缺省尺寸
  `open_or_create` 了 `doc_id` ⇒ 工具跑到时目标**已经存在** ⇒ 正确的"打开"分支被**变成**错误的分支。

**规则**：
1. 调查工具行为时，**先看入口怎么准备 `ctx`**（预建／预打开／参数改写），再看工具本身。
2. **不要相信文档注释**：本例里 `document_mut` 的注释写着"打开（或按需创建）"，与实现**相反**，
   它同时误导了外部报告与修的人。**以代码为准**；发现注释与实现相反时**顺手改注释**。

### 9.15 连续 push 会**取消进行中的 CI**（流程）
`ci.yml` 配了 `concurrency: … cancel-in-progress: true` ✓ —— 这是**对的**（CI 的目的是验证 HEAD ✓），
但**一轮推一次** ✗ 会让**每次 push 取消上一次**的 run ✗；而一次完整 run 约 **12 分钟** ✓
⇒ **∴ 结果是永远看不到完整结论** ✓（实测：`pending` 1 个 ＋ `cancelled` 2 个 ＋ `in_progress` 1 个 ✓）。
**纪律**：① 一次只推一个**值得跑 CI** 的提交 ⇒ 推完**等结论**；② 期间**只做**本地快检能覆盖的工作；
③ 需要连续提交就**先本地攒着** ⇒ **一次推**；④ `pending`／`in_progress` **不是结论**；
⑤ 查结论用 `gh run view --job <id> --log` ✓（**已证明能取到失败判据名 ✓**）。
