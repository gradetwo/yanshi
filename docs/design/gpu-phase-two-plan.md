# 九、★ **规模曲线：两本账都赢，幅度 73–95%**（第 247 轮）★

## 一、★ 实测（**浏览器内核，WebGPU 可用 ✓**）★

| 规模 | **① 时间账（**墙钟 ms ✓）** | **② ★ CPU 占用账 ★（**主线程 `TaskDuration` ms ✓）** |
|---|---|---|
| **1 M 像素** | **CPU 575.0 ⇒ GPU **31.3**** | **CPU 584.5 ⇒ GPU **38.9**** |
| **4 M 像素** | **CPU 2175.6 ⇒ GPU **572.6**** | **CPU 2183.1 ⇒ GPU **575.8**** |

**∴ 收益 ✗**：
- **1 M**：**时间 **−94.6%****｜**CPU **−93.3%**** ✓
- **4 M**：**时间 **−73.7%****｜**CPU **−73.6%**** ✓

**⇒ ★★ 两条账**同向且**幅度巨大**** ✗ ⇒ **∴ 而**这正是**用户第 594 轮**要的**两本账** ✓ ★★**

## 二、★ 一个必须说清的反差（**如实 ✓**）★

**∴ 上一跑（**第 245 轮 ✓，**同为 1 M ✓）✗**：
**CPU 580.0｜GPU 570.0** ⇒ **∴ 只快 **1.7%**** ✓
**⇒ 而这一跑**：**CPU 575.0｜GPU **31.3**** ⇒ **∴ 快 **94.6%**** ✓
**⇒ ★ 所以**：**上一跑的 GPU 路径**没真正走 GPU** ✗
**∴ 最可能**：**冷启动／首次创建 `GPUDevice` 的开销被算进了那一跑** ✓
**⇒ ∴ 所以**：**GPU 的测量必须**先热身一次**✗（**∴ 与 `tool-cpu-cost-repeated.mjs` 剔除第一轮同一个道理 ✓）★**** ✓✓

## 三、★ 4 M 的幅度**小于** 1 M（**怎么读 ✓**）★

**∴ 1 M −94.6%**✗ **而** 4 M −73.7%** ✓
**⇒ ∴ 因为**：**4 M 的 CPU 基线**更大（**2175.6 ms ✓）✗
**∴ 而** GPU 时间**也**从 31.3 涨到 **572.6 ms**（**×18**✗，**而**像素只 **×4**** ✓）
**⇒ ★ 所以**：**那里面含**数据传输／读回**的开销** ✓（**∴ 4 M × 4 B ＝ **16 MB** 的上传 ＋ 读回 ✓）
**∴ 而与**裁定档第 81 轮「**大输入上 GPU 赢得更多**」**看似矛盾**✗
⇒ **∴ 但**口径不同**：**第 81 轮**比的是**GPU 内部效率**✗、**这一跑**比的是**端到端（**含传输 ✓）** ✓★**** ✓✓

## 四、★ 对阶段二的结论 ★

**★ 量化这一步**：**浏览器内核的 WebGPU **两条账都大幅赢**** ✗
**⇒ ∴ 所以**：**它**支持**引入服务端 `wgpu`**（**裁决 3 ✓）✓
**∴ 而**服务端**不同**：**没有 16 MB／帧的上传**（**数据本来就在进程内 ✓）⇒ **∴ 传输开销**应当**小得多** ✓
**⇒ ★ 所以**：**服务端的收益**预期**≥ 浏览器内核**（**∴ 但仍**必须实测 ✓）★**** ✓✓
