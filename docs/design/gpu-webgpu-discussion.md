# 讨论：GPU 与 WebGPU 在本项目的取舍

**结论先行**：**现在不引入 GPU ✗**；**先按 [`offline-latency-plan.md`](offline-latency-plan.md) 把服务器已验证的
两层缓存 ＋ 免编码直通搬进内核 ✓**。**若将来要碰 GPU ⇒ **必须分层**✗：**CPU 是真值 ＋ GPU 只做显示级
或"不写回真值"的预览 ✓**。理由见下（**含两面 ✓**）。

## 一、现状（**实测 ✓**）

| 项 | 事实 |
|---|---|
| **GPU 依赖** | **`Cargo.toml`／各 crate 里**零命中**✗（`wgpu`／`web-sys`／`webgpu` 都没有 ✓）** |
| **shader／WGSL／WebGL** | **全仓库零命中 ✗** |
| **内核形态** | **`crates/yanshi-wasm/src/{lib,kernel,brush}.rs`** —— **纯 CPU 的 Rust→wasm** ✓ |
| **浏览器出图** | **`kernel.getContext("2d")`** ⇒ **2D canvas** ✓；**已有 `serverInk` vs `canvasInk` 逐像素对比 ✓** |

## 二、GPU 能解决什么／**不能**解决什么

**能**（**逐像素、可并行**）：**图层合成（blend ＋ 逐层采样）｜笔刷 dab｜滤镜（卷积）｜缩放／降采样**

**不能**：**实测瓶颈是"是否命中缓存"，不是"算得多快"**：

| 档 | 延迟 | 相对冷 |
|---|---|---|
| **外层 `region_cache` 命中** | **9.9 ms** | **≈5.8×** |
| **内层 tile（below）命中** | **48.8 ms** | **≈1.2×** |
| **全 miss（重渲）** | **46–58 ms** | 1.0× |

⇒ **5.8× 来自**不再算**，不是来自**算得快**** ⇒ **GPU 只改善"miss 那一档有多慢"，对"命中即秒回"无增益**。

## 三、与仓库硬约束的**真实冲突**（**比性能更重要**）

AGENTS.md 要求逐项核对「收益量级／体积／**确定性**／平台支持／供应链／构建时间／维护状态」，
且注明 **`yanshi-wasm` 的体积与确定性权重更高**。

| 因素 | WebGPU 实际情况 |
|---|---|
| **★ 确定性 ✗** | **GPU 浮点不保证逐位一致**（同驱动同卡也可能因 tile 划分／FMA 收缩而不同）—— **而本仓库有大量"逐字节相同"判据**（`incremental_stamp_matches_full_tile_re_render`／golden PNG／`serverInk` vs `canvasInk`）⇒ **一上 GPU 这些会红** ⇒ **与"绝不许撒谎"正面冲突** |
| **体积 ✗** | `wgpu`（wasm 目标）**很大**，而 `yanshi-wasm` 的体积权重**最高** |
| **平台支持 ✗** | **WebGPU 浏览器支持面仍窄** ⇒ 必须**保留 CPU 路径** ⇒ **两套实现 ⇒ 维护成本翻倍** |
| **供应链／审计 ✗** | 图形栈依赖多（naga／hal／驱动）⇒ 审计面扩大 |
| **收益量级 ✓** | 合成是逐像素，理论上 10× 级；**但**受显存带宽与上传／下载限制，**小区域（如 512²）的收益会被传输开销吃掉** |
| **构建时间 ✗** | wasm ＋ wgpu 明显变长 |

## 四、分层方案（**如果将来要做**）

**原则**：**CPU 是**真值**，GPU 是**可选加速**，且**逐位一致只在 CPU 上承诺**。**

| 选项 | 做法 | 何时选 |
|---|---|---|
| **A ★ 现在推荐 ★** | **不引入 GPU**；**先把两层缓存 ＋ 免编码直通搬进内核** | **有实测依据（5.8×／1.2×）＋ 零确定性风险** |
| **B** | **GPU 只做**显示级**：缩放／平移插值 ＋ 悬停高亮**（**不参与像素真值**） | 想让"看"更顺滑时，风险最低 |
| **C** | **GPU 参与合成，但**结果不写回真值**：只作预览；导出／判据仍走 CPU** | 若能接受"**预览与导出可能有 ±1 色差**"（**必须写明两面**） |
| **D ✗ 不推荐** | **GPU 作为唯一合成路径** | **直接撞上"逐字节相同"与"不许撒谎"** |

## 五、∴ 行动

1. **现在**：按 [`offline-latency-plan.md`](offline-latency-plan.md) 搬运**两层缓存 ＋ 免编码直通**（**选项 A**）。
2. **若将来要碰 GPU**：**先立分层规则**（CPU 真值 ＋ GPU 只做预览／显示级），
   **并先写一条**红判据**证明"预览与 CPU 的色差有界且已如实报出"** ——
   **否则不许合入**（**目标纪律：不许用降精度换速度而不写两面**）。

## 六、★ **决定（**用户 ✓，第 591 轮 ✓**）** ★

**用户明确指示**（**原文要点 ✓**）：
> **离线渲染应该尽可能 webgpu，不支持时候才 fallback cpu。服务端也是应该提高有 GPU，默认使用 GPU，
> 支持 fallback CPU，且参数支持关闭 GPU。做不到一致就牺牲点一致性，wasm 体积也是该牺牲就牺牲。**

⇒ **∴ 本节**覆盖**前面第四节的推荐 ✗**（**§4 的选项 A "现在不引入" 不再采用 ✗**）。
**∴ 而 §3 的代价分析**仍然有效 ✓** —— **∴ 它现在是**已知代价清单**✗，**不是"不做的理由"✓**。

### 6.1 决定摘要

| 面 | 决定 |
|---|---|
| **离线（**内核 ✓**）** | **尽可能用 WebGPU ✓**；**不支持 ⇒ fallback CPU ✓** |
| **服务端** | **默认用 GPU ✓**；**支持 fallback CPU ✓**；**参数可关闭 GPU ✓** |
| **一致性 ✗** | **做不到完全一致 ⇒ **接受一点差异**✓**（**∴ 但必须**量化并如实报出**✗，见 6.3 ✓**） |
| **体积 ✗** | **接受 `wgpu` 带来的体积增长 ✓**（**∴ 含 wasm 内核 ✓**） |

### 6.2 与目标纪律的关系（**必须守住的三条 ✓**）

1. **"不许撒谎"** ✓ ⇒ **∴ 差异**必须可见**✗**：**响应／诊断里报出**当前后端**✗
   （**如 `render_backend: "gpu" | "cpu"` ✓**）＋ **与 CPU 判决的**最大通道差**✗**
   （**如 `max_channel_delta: u8` ✓**）。
2. **"先测量再改"** ✓ ⇒ **∴ 上 GPU 前**先量 CPU 基线（**已有 ✓**：**三档 9.9 ／ 48.8 ／ 46–58 ms ✓**），
   **∴ 上 GPU 后再量同一组 ✗** ⇒ **∴ 才有"GPU 到底快多少"的**实数**✗**。
3. **"不得用降精度换速度而不写两面"** ✓ ⇒ **∴ 本文件 §3 ＋ 6.3 就是那两面 ✓**。

### 6.3 **牺牲一致性**的可红判据（**先立它，再上 GPU ✓**）

| # | 判据 | 期望 |
|---|---|---|
| **①** | **同一文档、同一区域 ⇒ GPU 与 CPU 各渲一次 ⇒ 逐像素比较** | **`max_channel_delta ≤ 1`** ✓（**∴ 若 > 1 ⇒ 红 ✓**） |
| **②** | **GPU 不可用时 ⇒ 自动 fallback CPU ⇒ 结果**与 CPU 基线逐字节相同** | **`diff == 0`** ✓ |
| **③** | **参数关闭 GPU ⇒ 走 CPU ⇒ 与基线逐字节相同** | **`diff == 0`** ✓ |
| **④** | **响应／诊断必须报出**后端 ＋ 最大通道差** | **`render_backend` / `max_channel_delta` 存在 ✓** |

**∴ 且**：**① 的 `≤ 1` 是**当下的目标值 ✗** ⇒ **∴ 若实测更大 ⇒ **∴ 不许悄悄放宽 ✗**
（**∴ 要么改算法 ✓，要么**改判据并写明代价 ✓**）** ✓✓

### 6.4 我对 §3 分析的**保留意见**（**如实 ✓**）

**我仍然认为**确定性冲突是真实的 ✗** ⇒ **∴ 但**用户已决定接受它 ✓** ⇒
**∴ 所以我把**"接受多少"变成 6.3 的可红判据 ✗** —— **∴ 这样"牺牲"是**有界且可见**的 ✓，
**而不是**悄悄变糊 ✗** ✓✓
