# 颜料混色（P2 #16）的现状、实测与决策

日期：2026-10-15
基线：`af8babab`（main）＋ l4-sync 上的 P0/P1 一批
需求出处：`~/patch/yanshi-引擎MCP需求建议-20261014.md` 的 P2 #16

## 一、需求要什么

> 颜料混色（**必须 Clean-Room**：Mixbox 是 CC BY-NC 不能碰；首选 MIT 的 neco-pigment，
> 备选 PBM 思路或纯 K-M 自实现；`color_mixing: "rgb"|"pigment"`，默认 rgb）

**目标场景**：黄 + 蓝要混出**绿**（减色混合），而不是 RGB 插值给出的**灰**。

## 二、先做了什么（本轮实测）

在 `yanshi-render/src/color.rs` 里按**纯 K-M 自实现**写了一版最朴素的模型：

* sRGB 字节 → 线性光（复用仓库既有的 `byte_to_linear`，逐位可复现）；
* 每通道换算到 `K/S = (1-R)² / (2R)`（K-M 两常数近似里 **K/S 对混合是线性的**），
  以 `K/S = (1-t)·KS_a + t·KS_b` 混合，再反解 `R = 1 + KS - sqrt(KS² + 2·KS)`；
* `R` 设下限 `1/255`（线性域一个字节），避免 `K/S` 发散。

**实测结果（决定性判据，`cargo test -p yanshi-render --lib pigment`）**：

```text
黄 (255,255,0) + 蓝 (0,0,255)，t = 0.5
  RGB 线性插值  => [128,128,128]   （灰 ✓，符合预期）
  逐通道 K-M    => [  2,  2,  2]   （近黑、**没有任何偏色** ✗）
  期望          => 偏绿（G 高于 R 与 B）
```

判据的断言是"**颜料混色必须偏绿**（`G > R` 且 `G > B`）" —— 它**红了**，红得对 ✓。

## 三、为什么逐通道模型不可能做对（这是本轮的结论）

黄颜料的反射是"**红 + 绿**"，蓝颜料是"**蓝**"。真实颜料混色的结果偏绿，靠的是**宽而平滑的
光谱反射曲线**在**波段之间**的叠加（黄在蓝波段仍有一点反射、蓝在绿波段也有一点）。

而**逐通道**模型把三个通道当成**互不相干的标量**：

* 黄的蓝通道是 0 ⇒ `K/S` 极大；
* 蓝的红/绿通道是 0 ⇒ 同样极大；
* 混合后**每个通道都极大** ⇒ `R` 全被压到接近 0 ⇒ **近黑** ✗。

**所以"纯 K-M 自实现"要想做对，必须把颜色投到若干**光谱波段**上再混**（这正是需求里
"备选 PBM 思路"的意思）：PBM 那一类做法用 **8 个左右**的波段基，neco-pigment 用更多基函数
（学出来的）。**逐通道是不可能的**，不是"参数没调好"。

## 四、决策（按 AGENTS.md 的依赖取舍清单）

1. **不发布一个"pigment"模式**：`color_mixing: "pigment"` 若给出 `[2,2,2]`，
   比"没有这个功能"更糟（用户会以为能混色）。本轮把试验**撤回**，`color.rs` 回到原状 ✓。
2. **下一步优先评估 `neco-pigment`（MIT）**，逐项核对 AGENTS.md 的因素：
   * **收益量级**：把"黄+蓝=灰"变成"黄+蓝=绿" ⇒ 对"维梅尔级"混色是**根上的**差别；
   * **体积**：要看它的基函数/查表有多大 —— 对 `yanshi-wasm`（浏览器内核）**权重更高**；
   * **确定性**：必须是纯函数、无随机、无平台分支（否则与本仓 D0 基线冲突）；
   * **平台**：`wasm32` 与桌面都要能编译（本仓 already 有 `libm` 口径）；
   * **供应链与审计面**：MIT、单一来源、可读；
   * **构建时间与工具链**：不能引入需要额外工具链的生成步骤；
   * **维护状态**：是否活跃、有无替代。
   * **结论要求**：提交与报告里**两面都写**（好处与代价缺一不算完成 —— AGENTS.md 原话）。
3. **若评估不通过**，退路是自己实现一个**8 波段**的 PBM 风格基：
   * 需要一份**可引用的公开基数据**（注意许可）；**不能**从参考图取像素（本仓硬约束"不作弊"）；
   * 8 波段的换算表体积可控 ⇒ 对 wasm 友好；
   * 判据仍然是这一条**决定性**的红/绿对照（黄+蓝必须偏绿；RGB 模式必须仍是灰）。
4. **接口形状先定下来**（本条不影响后面选哪种实现）：
   * `brush_stroke`（以及 `color_to` 渐变路径）加 `color_mixing: "rgb"|"pigment"`，**默认 `rgb`**；
   * `rgb` ⇒ 与今天**逐字节相同**（既有像素判据一位不动）；
   * `pigment` ⇒ 只在**显式要求**时生效（opt-in，零爆炸半径 —— 与本会话 `dwell`/`glaze` 同规矩）。

## 五、本轮之后的状态

* `color_mixing` **尚未**接进任何工具（因为它还没有可信的实现）。
* 判据**尚未**落盘：它得等实现选型，否则就是"为不存在的功能写门槛"。
* 这条的**决定性判据**已经写清楚（黄+蓝 ⇒ 偏绿；RGB ⇒ 灰），随时可以红着先落地。
