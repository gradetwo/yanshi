# 整幅渲染的内存账目（DEF-03 / 8K OOM 的根因调查）

日期：2026-10-15
基线：`c45e4b30`（main）
判据：`scripts/tool-render-memory-budget.mjs`（**当前已知红**，见 `scripts/criteria-known-red.txt`）

## 一、已经被实测钉死的账目

判据量的是「4K ＋ 4 层真实素材，**整幅渲染那一步的 RSS 增量**」（数据取自 `GET /health` 的
`rss_bytes`，所以不必新增 API、也不必读 `/proc`）。

| 场景 | 实测 | 说明 |
|---|---|---|
| 空载 ／ 4K 空文档（未渲染） | 4 MB ／ **5 MB** | 图层像素是**懒分配**的 |
| 导入 4 层小素材（900×640 ≈ 2.3 MB/张） | 151 MB | 每张 ≈ 50 MB（解码后的 tile 存储） |
| **4K ＋ 4 个空层 ⇒ 整幅渲染** | 72 ⇒ **1032 MB**（增量 ≈ **960 MB**） | ≈ 4 × 240 MB ⇒ **每层一个全幅 f32 工作缓冲** |
| 单层 4K 空文档 ⇒ 整幅渲染 | +52 MB | 说明渲染路**本身**是分块的 |
| 判据实测（4 层真实素材） | 增量 **895–909 MB** | 稳定复现 |

**结论**：这笔账与**图层数**成正比、与渲染面积的关系弱 ⇒ **每层一个全幅（或按 chunks 分带）的
f32 工作缓冲，且多层同时在用**。

## 二、代码位置（已读）

* 生产路径：`render_region`（`crates/yanshi-render/src/render.rs:1056` 起）
  * 当 `workers > 1 && region_pixels >= PARALLEL_MIN_PIXELS` ⇒ 走
    `parallel_impl::render_region(...)`（**按行分块**）
  * 之后 `self.buffer_pool.begin_render_with(chunks, 2)`（`render.rs:4058`）
    ⇒ **池的并发因子 = chunks × 2**
* 合成循环：`for layer in state.alive_layers()`（`render.rs:2058` 起），每层
  `self.buffer_pool.acquire(origin_x, origin_y, width, height)`（`render.rs:2099`）
* 池的预算公式（`buffer_pool.rs`）：`max(MIN_POOLED_BYTES=192 MiB,
  并发 × 每并发块数 × 本轮最大单块)`，**已加**绝对上限 `MAX_RETAINED_BYTES = 384 MiB`
* 缓冲区大小：`Buffer::new` 里是 `vec![0.0; w*h*4]`（**f32** ⇒ 4096² 一张就是 **268 MB**）

## 三、可调的旋钮（按"收益/风险"排序）

1. **`chunks`（并发分块数）** —— **已实测，结论是"不能只靠它"**（第 254 轮）。
   仓库本来就有诊断开关 `YANSHI_BAND_CAP`（覆盖 `DEFAULT_BAND_CAP = 2`，见 `render.rs:303`），
   所以**不改一行代码**就能量。内存判据（4K ＋ 4 层真实素材，整幅渲染的 RSS 增量）：

   | 带数上限 | 内存增量 | 说明 |
   |---|---|---|
   | **1** | **543 MB** | **低于 800 MB 预算**，但见下面的墙钟 |
   | **2（当前默认）** | **889 MB** | 现状（判据红） |
   | 4 | 905 MB | 与 2 差别不大 |
   | 8 | 924 MB | 同上 |

   两本账（同机、4K＋4 层、中位数、热身剔除）：
   * 带数 **2**（默认）：墙钟 **49.3 ms**｜CPU 40.0 ms｜预热 3.5 s｜峰值 RSS 1575 MB
   * 带数 **1**：墙钟 **536.8 ms**｜CPU 520.0 ms｜预热 **54.5 s**｜峰值 RSS 1111 MB
   => **带数 1 能把内存压进预算，但渲染慢 10 倍**（没有并行度了）=> 违反"4K 一笔 ≤ ~100 ms"
   => **不能把默认降到 1**。
   * **补充纠正**：`render.rs` 里那段"带数少 ⇒ 渲染更快"的实测比的是 **2 vs 8**（不是 1）；
     到 **1** 就完全没有并行了，结论翻转。

   **⇒ 所以内存这笔账靠"夹带数"解决不了**：便宜的方向只有两个，**两个都试过了** ——
   夹**保留量**（11× 慢，见旋钮 4）与夹**带数**（10× 慢）—— 都不行。
   真正的解要么**降低单块字节**（旋钮 2：f32⇒f16），要么**让单块变小**（旋钮 3：分块/分带合成）。
2. **工作缓冲从 f32 降到 f16** —— 仓库已有 `crates/yanshi-render/src/half.rs`。
   单块 268 MB ⇒ 134 MB。**风险**：会改变渲染的数值 ⇒ 现有像素级判据可能红，
   属于"精度换内存"的取舍，需要先量清楚对画质的影响。
3. **真正的分带合成** —— 让合成**一条带一条带**地做（`begin_render(1)`，
   每带合成完立刻释放），峰值 ≈ 一条带。**风险**：改动面最大，且要确认
   src-over 的可结合性（它可结合 ✓）与图层缓存的交互（读画布类笔刷已禁用缓存 ✓）。
4. **`MAX_RETAINED_BYTES`（曾加 384 MiB）—— **试过、已撤，别再走这条路**。
   同机 A/B（4K ＋ 4 层真实素材、中位数、热身剔除）：
   * 有上限：墙钟 **519.9 ms**｜CPU **510.0 ms**｜预热 **41.0 s**｜峰值 RSS **1567 MB**
   * 无上限：墙钟 ** 47.0 ms**｜CPU ** 40.0 ms**｜预热 ** 3.4 s**｜峰值 RSS **1573 MB**
   => **11 倍 CPU 回归，内存一点没省**。原因：上限让**归还的块被丢弃** => 每层都要重新分配
   268 MB 的 f32 缓冲（4K × 4 层 ⇒ 十几次 malloc/free 与 page fault）。
   **教训**：判断"某个上限无害"不能只靠推理（"它只管保留、不该影响在用"）—— **必须两本账量**；
   我当时只量了内存（909 ⇒ 895 MB，判为噪声），**没有**同时量墙钟/CPU 的 A/B，
   于是把一个 11 倍回归留在了 main 上（第 254 轮才发现并撤掉）。

## 七、★ 第 254 轮的更正：**"每层一个全幅缓冲"这条账目是错的** ★

用新脚本 `scripts/tool-render-memory-attribution.mjs` 做了**同机扫描**（`--side 2048`，只读
`/health` 的 `rss_bytes`，每步取稳定值）：

| 层数 | 渲染前 | 渲染后 | **增量** |
|---|---|---|---|
| 1 | 8 MB | 327 MB | **319 MB** |
| 2 | 344 MB | 585 MB | **241 MB** |
| 3 | 585 MB | 889 MB | **304 MB** |
| 4 | 889 MB | 1129 MB | **240 MB** |

**两条硬结论**：
1. **每次整幅渲染都 +240–320 MB，与层数无关** ✗ —— 所以"**每层**一个全幅 f32 缓冲且同时在用"
   **站不住**。当初 4K＋4 层量到 ~960 MB，960/4 = 240 正好是这个常数 => 我被这个数字巧合骗了。
2. **增量不回落**（RSS 单调 327 ⇒ 585 ⇒ 889 ⇒ 1129 MB）=> 是**保留**，不是"同时在用"。

**真机制（同一次 `/health` 直接读出来的）**：

```text
cache:        tiles = 256   used_bytes = 134,217,728 (128 MB)
              pixel_bytes_estimate = 234,881,024 (224 MB)
              hits = 0  misses = 256  evictions = 0     <-- 从不淘汰
region_cache: hits = 0  misses = 4  evicted = 0
bitmap_cache: hits = 0  misses = 0
```

=> **tile 缓存没有任何上限、也从没淘汰过** ✓ —— 这与需求文档里"分块/别同时活着"的方向一致，
但**修的应该是缓存的**预算/淘汰**，而不是"合成时别同时持有" ✗（后者我曾按那条账目去改，
结果两次都撞在别的地方：夹保留量 11× 慢、夹带数 10× 慢）。

**下一步（建议，且不在长会话尾端动）**：
1. 给 tile 缓存加**字节预算 ＋ LRU 淘汰**（`evictions` 必须开始动），并用本节的扫描脚本复量：
   目标是在 4 层 4K 场景把"每次渲染的增量且不回落"压回**接近 0**；
2. 同时量**两本账**（墙钟 ＋ CPU，中位数与极差）—— 淘汰策略可能让重渲变慢，必须一起看；
3. `region_cache` 的 `misses=4 / hits=0 / evicted=0` 也要一并看：它同样没有任何淘汰迹象。
4. **注意**：本机 3.8 GB RAM 下，`--side 4096` 的四层扫描会**把机器压到 OOM**
   （第 254 轮实测：整条命令被 SIGKILL，连带把服务进程带走）=> 4K 只做"单次渲染前后"，不要扫层数。

## 八、★ 第 254 轮的**再更正**：第七节里那句"无上限 tile 缓存"**也是错的** ★

第七节我读到 `/health` 的 `cache`（256 tiles／used 128 MB／`evictions = 0`）就下了结论
"tile 缓存没有上限、从不淘汰"。**核对代码后这句话站不住** ✗：

* `/health` 的 `cache` 来自 **`workspace.cache_stats()`**（`crates/yanshi-http/src/server.rs:1272`）
  —— 那是**工作区的文档 tile 存储**（持久存储 ✓），**不是**渲染器的 `TileCache` ✗。
  它的字段里还有 `pixel_bytes_estimate`，而 `TileCacheStats`（`render.rs` 用的那个）
  **没有**这个字段 => 两者根本不是同一个东西 ✓。
* 真正的渲染器缓存 `TileCache`（`crates/yanshi-render/src/tile.rs:437`）：
  `Renderer::new` 给的预算是 **64 MB**（`render.rs:895`），而且 `insert` 里**会**调 `evict_to_fit()`
  => 它**有界且会淘汰** ✓，不是"无上限" ✗。
* 所以文档 tile 存储里 `evictions = 0` 是**正常的**（那些文档还开着，属于存储不属于缓存）。

**于是正确的一条（与实测数字对得上）**：
* 2048² 的一整幅 f32 单块 = 2048×2048×16 B = **64 MB**；
* 每帧同时在用的是 **`chunks × 2`** 块（`begin_render_with(chunks, 2)`）=> `chunks = 2`（默认
  `DEFAULT_BAND_CAP = 2`）=> **≈ 256 MB**；
* **实测每次整幅渲染 +240–320 MB** ✓ ⇒ **吻合** ✓。
* **与层数无关** ✓（缓冲是**按 band/帧**分配的，不是按层 ✗）；
* **不回落**是因为这些块归还后进了 **`BufferPool`** 并被**保留**（预算 =
  `max(MIN_POOLED_BYTES = 192 MiB, 并发 × 每并发块数 × 本轮最大单块)`）=> RSS 停在高水位 ✓。

**所以修法回到两处，而不是"缓存淘汰"**：
1. **峰值**：让"同时在用的块"变小 —— 分带合成（`chunks` 已经默认 2，再小就掉并行，实测 1 band
   会慢 10 倍 ✗）或让单块变小（f16 ✗ 会改数值，需要画质判据）；
2. **保留**：`BufferPool` 的预算 —— 我已经试过用绝对上限夹它，结果 **11× 慢**（见第五节旋钮 4），
   已撤；要再动它，必须先有"内存 vs 墙钟/CPU"的**同机 A/B**，且要解释为什么夹保留量会影响速度。

**★ 本节的教训（写在这里）★**：我在这个题目上**连续错了三次**（"每层一个缓冲"✗、
"无上限 tile 缓存"✗、早先的"import_image 1.7 GB"✗，后者已撤）。三次都是**拿一个数字当了结论** ✓。
下次动它之前，先做一件我现在还没做的事：**给渲染过程加一个"分配点 + 字节数"的探针**
（`/health` 的聚合计数做不到这件事 ✗）=> 有了它，账目才不再是推断。

## 九、★ 第 254 轮：**分配探针**上线 ＋ **第一次直接归因** ★

第八节结尾我写了"下次动它之前先做一件我还没做的事：给渲染过程加'分配点 + 字节数'的探针"。
**这一轮做完了**：

* `crates/yanshi-render/src/alloc_probe.rs`：**定长数组 + 原子**（无锁、无分配，不会因为记录分配而
  自己产生分配）；按固定分配点分类；**门控 `YANSHI_ALLOC_PROBE`**（环境变量每进程读一次 =>
  生产路径零开销，与 `YANSHI_RENDER_PROBE` 同规矩）。
* 接入三个点：`BufferPool::acquire` 的**命中（复用）**与**未命中（新分配）**、以及
  **`Buffer::new`**（走 `vec![0.0; …]`、**绕过池**的那些路径）。
* `/health` 新增 `alloc_probe` 字段（关着时全 0）。

**第一次直接归因（本机，2048²，单层，单次整幅渲染）**：

```text
渲染前： 全部 0
渲染后： buffer_fresh  268,435,456 B (256 MB) / 69 次   <-- ★ 绕过池 ★
         pool_fresh     67,108,864 B ( 64 MB) /  2 次
         pool_reuse     67,108,864 B ( 64 MB) /  2 次
         pool_release  134,217,728 B (128 MB) /  4 次
RSS: 7 MB => 311 MB    （增量 +304 MB，与第八节层数扫描的 +319 MB 吻合）
```

**两条结论（这次是实测，不是推断）**：
1. **一帧里真的有 69 次 `Buffer::new`、合计 256 MB 完全绕过缓冲池** ✗ ——
   池只看到了 2 次新分配 + 2 次复用（各 64 MB，正好是 2048² 的两个 band 块）。
   => 要压峰值/保留，**主战场在这些绕过池的分配**，而不是池的预算（后者我夹过、11× 慢、已撤）。
2. RSS 增量（+304 MB）**大于**池里经手的量（64+64−128 的净额）=> 差值主要来自那 256 MB，
   且它**归还后没有回落**（第八节的层数扫描里 RSS 单调上升）=> 要么是分配器驻留，
   要么有地方**持有**了这些缓冲。

**下一步（明确、可判）**：
1. 找那一帧里的 69 次 `Buffer::new` 调用点（探针已能给出**次数与字节数**；要定位到**代码位置**
   就给探针加一个"点名字符串"维度，或直接在可疑调用点上临时加 `record(Other, …)` 分组）；
2. 把它们**收进池**（或确保帧末 `drop` 并及时 `malloc_trim` 级别的归还策略）；
3. 复量：`alloc_probe.buffer_fresh` 应当接近 0、且 `rss` 在一帧后回落；同时量两本账（墙钟 + CPU），
   因为"池化更多东西"可能改变速度。

## 十、★ 第 254 轮：归因**精确到函数** —— 那 69 次是 `Buffer::crop` ★

第九节的探针只能给出"哪个分配点、多少字节"（"256 MB / 69 次绕过池"），但**不知道是哪 69 次**。
本轮给探针加了 **`#[track_caller]` + `Location::caller()`** 的**调用点维度**（只在探针开着时进表 =>
生产仍是一次 `OnceLock` 读 ✓），`/health` 新增 `alloc_probe_sites`（按文件聚合）。

**复量（2048² 单层单次整幅渲染）**：

```text
alloc_probe:       buffer_fresh 268,435,456 B / 69 次
alloc_probe_sites: crates/yanshi-render/src/buffer.rs       134,217,728 B / 66 次   <-- 主犯
                   crates/yanshi-render/src/buffer_pool.rs   67,108,864 B /  2 次
                   crates/yanshi-render/src/render.rs        67,108,864 B /  1 次
```

再顺着"`buffer.rs` 内部哪里会 `Buffer::new`"查下去 ⇒ **生产代码里只有一处**：

```rust
// crates/yanshi-render/src/buffer.rs:454
pub fn crop(&self, bbox: &Bbox) -> Buffer {
    let mut out = Buffer::new(x0, y0, width, height);
    ...
```

=> **66 次（128 MB）全部来自 `Buffer::crop`** ✓✓ —— 渲染路径在**大量裁剪缓冲**，
而每次 `crop` 都**新分配一个 `Buffer`、绕过缓冲池** ✗（池只管着 2 个 64 MB 的 band 块）。

**这就是"每次整幅渲染 +240–320 MB 且不回落"的可操作根因** ✓（第一次是在数据上看到它、
第二次是在文件上看到它、这次是在**函数**上看到它）。

**下一步（已可执行）**：
1. `crop` 目前返回**独占**的 `Buffer` => 要池化它，得让热路径改用一个**可复用的 scratch**
   （或让 `crop` 有 `crop_into(&mut Buffer)` 的变体、由调用方从池里借）=> 先数清热路径有哪几处调它；
2. 复量：`alloc_probe.buffer_fresh` 应接近 0、且一帧后 `rss` 回落；
3. **同时量两本账**（墙钟 + CPU）—— 池化会改变内存流量，可能影响速度；
4. 别忘了那条硬约束：**4K 上一笔 ≤ ~100ms**。

## 十一、★ 第 254 轮：`crop` 的**调用点清单**与两条改进轴（结构性改动，留给专门一轮）★

第十节把 66 次分配定位到 `Buffer::crop`。本轮把**热路径的调用点**也列清楚（`render.rs`）：

| 行 | 调用 | 形态 |
|---|---|---|
| 648 / 654 | `dst.crop(area)` / `src.crop(&same)` | 合成辅助（每次调用） |
| 1199 | `accumulation.crop(&region)` | **整帧输出**裁剪（每次渲染 1 次） |
| **2263** | `accumulation.crop(&bbox)` | **循环里按 bbox 逐块**（最可疑） |
| **2427** | `above_acc.crop(&bbox)` | 同上（above 层） |
| 3625 | `layer_buffer.crop(&snapshot_bbox)` | 单层快照 |
| 4391 | `buffer.crop(region)` | 见 4398 的注释：**旧实现曾经裁剪整帧**，已经有人把它改掉了 ✓ |

**两条独立的改进轴**（不要混为一谈）：

1. **峰值**（同时在用的字节）：把 2263/2427 这两处在循环里的 `crop` 改成"**从池里借 + `crop_into`**"，
   或者干脆让下游接受"**区域视图**"而不是一个新 `Buffer`。**代价**：这两处会把 `Buffer`（独占值）
   传进下游函数 => 要改**跨函数签名** ✗ —— 本会话我已经因为"跨签名的大编辑"回退过两次
   （`time_ms`、`glaze`），所以这条要么分小步做、要么先设计出"借用型视图"再动手。
2. **保留**（RSS 不回落）：`crop` 每次 malloc 一个约 2 MB 的块（66 × 2 MB ≈ 128 MB），
   归还后**不回落** => 这是**分配器**行为。可选做法：池化 scratch（同上，要改签名）／
