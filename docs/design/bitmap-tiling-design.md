## 四、方案（**A：切 tile，不改解压算法**）

**∴ 做法 ✗**：**位图**按 tile 切块**存储**✗（**tile 边长**是**实现常量** ✓）
⇒ **∴ 于是**解码**只碰**覆盖请求区域的**块** ✓。

**∴ 为什么选它（**对比 B ✗）**：
- **A** **只改范围**✗、**不改解压算法** ⇒ **∴ 于是**「**区域渲染与整幅渲染逐字节一致 ✓」那条绿判据**最容易**继续绿 ✓
- **B（换随机可访问格式）** **会动格式语义** ✗ ⇒ **∴ 风险更大 ✓

**★ 借鉴来源（**按要求点名 ✓）★**：
- **GIMP**：**tile 化脏区** ＋ **`GeglBuffer` 按需换格式** ✓
- **Krita**：**per-node paint device** ✓
- **★ 我们与它们的**差别**（**两面都写 ✓）★**：
  - **∴ GIMP 的 tile**是**渲染缓存**的单位**✗ ⇒ **∴ 而**我们的 tile**是**存储格式**的单位 ✓
  - **∴ 我们**不采用** Krita 的 **LoD** ✗ ⇒ **∴ 因为**承诺**逐位一致** ✓
  - **∴ 代价**：**存储块变多** ⇒ **∴ 元数据与 CAS 对象数上升** ✓（**∴ 收益**是**解码量降 73× ✓**）

# 八、★ **红灯的**真原因**：块粒度，不是缺陷**（第 219 轮）★

## 一、★ 直接跑判据（**不猜 ✓**）★

## 二、★ 算术：**≈2.24 块** ★

| 项 | 值 |
|---|---|
| **解码增量** | **146,944 B** |
| **÷ 4 B／像素** | **36,736 像素** |
| **请求区域** | **4,096 像素（**64² ✓） |
| **⇒ 倍数** | **9×** |
| **⇒ 折合块数** | **≈ 2.24 块**（**∴ 若**块是 **128² ＝ 16,384 像素 ✓）** |
| **阈值** | **65,536 B（**K=4 × 4096 × 4 ✓）** |

**⇒ ★★ 所以 ✗ ★★**：
**∴ 一个 64² 的请求**至少**要碰 **1 块**✗ ⇒ **∴ 而**跨边界时 **2×2 ＝ 4 块**** ✓
**⇒ ∴ 于是**：**解码量**天然** ≥ **块面积**✗ ⇒ **∴ 而**与**请求面积无关** ✓
**⇒ ★ 所以**：**阈值 `K × 区域像素 × 4`**对小于一块的请求**天然无法满足** ✗
**∴ 而那**不是**缺陷**✗ ⇒ **∴ 而是**「**块粒度**」与「**极小请求**」的**固有差距** ✓ ★**** ✓✓

**∴ 它的问题 ✗**：**区域小于一块时**✗ ⇒ **∴ 右边**可以**小于**一块** ✓**** ✓✓

**★ 判据侧的证据（**它自己打印的 ✓）★**：

- **「**区域 vs 整幅逐字节一致（**不一致 0 字节**）」 ✓
- **「**整幅也没有解码字节**」 ⇒ **∴ 说明**整幅**不必重解** ✓**** ✓✓
**⇒ ∴ 所以**：**分块路**确实在工作** ✗ ⇒ **∴ 唯一不达标的是**极小请求的块粒度开销** ✓**** ✓✓
