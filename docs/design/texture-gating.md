# 画布纹理门控（P1 ⑦）的现状核查与两条出路

日期：2026-10-15（第 254 轮）
需求出处：`~/patch/yanshi-引擎MCP需求建议-20261014.md` 的 P1 ⑦
结论：**按文档现在的写法"不适用"** —— 先给出证据，再给两条出路。

## 一、需求说了什么

> **P1 ⑦ 画布纹理门控**：按**绝对坐标哈希**生成纹理门控，dab 采样时判断是否跳过
> => 让**多笔的飞白纹理在空间上对齐**（像同一张画布）。

## 二、核查（本仓纪律：先查"有没有"）

| 核查项 | 实测 | 含义 |
|---|---|---|
| 自带笔刷里有几支带 `texture` 设置 | `grep -l '"texture"' assets/brushes/*.myb` => **0 支** | MyPaint 的纹理是**笔刷要引用一份纹理数据**才成立 => **没有纹理可用** ✗ |
| 自带笔刷里几支带 `gridmap` | **19 支** | `gridmap` 是给**纹理**做画布对齐用的（`GridmapX/Y`、`GridmapScale/X/Y` 在 `hokusai-core` 里都有 ✓）=> **没有纹理时它是惰性的** ✗ |
| "飞白"现在从哪来 | **介质路径**：`yanshi-medium-host` 的 `StrokeSettings`/`DabInput` 里有 `texture: f64`（`TextureSettings` 亦在） | 介质（水彩/油画那几支）**自己有纹理**，走的是**另一套机制** ✓ |

**所以**：⑦ 想解决的"多笔飞白对齐"这件事，在本仓当前形态里**不是缺一个门控**，而是
**缺一份（或一套）笔刷纹理资产** ✓。再往引擎里加一个 gridmap 门控，属于**重复造轮子** ✗
（`hokusai-core` 的 gridmap 就在这里 ✓，本仓的规矩是"引擎已有的 MCP 不做第二遍" ✓）。

## 三、两条出路（择一，各有明确代价）

### 出路 A：补纹理资产 + 接上引擎已有的 gridmap 通道

* **做法**：往 `assets/textures/` 里放一份（或几份）**可平铺的灰度纸纹/画布纹**，
  给需要飞白的笔刷（或给一个"纹理开关"参数）接上 `texture` + `gridmap_scale*`。
* **代价**：需要**选资产并注意许可**（仓库既有的 `Paper*.png` 是不透明照片，不适合当笔刷纹理 ✗
  —— 见 `scripts/tool-paper.mjs` 的 ③ 那条注释）；纹理本身要**确定性**、**可平铺**、**体积可控**
  （对 `yanshi-wasm` 体积权重最高 ✓）。
* **好处**：**不改内核** ✓（gridmap 与纹理采样都是引擎已有的 ✓）；飞白会**自动**按画布坐标对齐 ✓
  （因为 gridmap 就是干这个的 ✓）。

### 出路 B：把 ⑦ 并入**介质纹理**那条路，并改写需求文档

* **做法**：承认"飞白"由**介质**提供（`medium_params` 已有 `texture` ✓，见 P0 ⑤ 的判据
  `scripts/tool-medium-params.mjs`），把 ⑦ 的文字改成"**介质纹理的画布对齐**"，
  再单独评估介质路径的纹理是否**已经**按绝对坐标取样 ✓（若已按，则 ⑦ 可以直接判为"已满足" ✓）。
* **代价**：需要**改写用户的需求文档**（那是用户的文件，应由用户决定 ✗）；
  且介质纹理的对齐性**还需要实测确认** ✗（我这一轮没测）。
* **好处**：不需要新资产 ✓，方向与本仓"介质管干湿纹理"的分工一致 ✓。

## 四、下一步（无论选哪条，**先做这一件**）

**实测介质纹理的对齐性**：同一块画布上画两笔部分重叠的介质笔触（带 `texture`），
比较**重叠区**的纹理图案是否一致：

* 如果**一致** => ⑦ 想要的"多笔飞白对齐"其实**已经有了**（在介质那条路上）=> ⑦ 应判为"已满足"，
  只需补一条判据把它钉住 ✓（最省 ✓）。
* 如果**不一致** => 说明介质的纹理是**按每笔**取样的 => 那么"按绝对坐标对齐"才是真缺口，
  此时才需要在介质路径上把取样坐标从"笔触相对"换成"**画布绝对**" ✓（这比给 `.myb` 补纹理资产更聚焦 ✓）。

**这个实验很便宜**（两次 `medium_stroke` + 一次逐像素比较），而且**结论直接决定走 A 还是 B** ✓ ——
所以它是下一轮做 ⑦ 的**第一步**，而不是先动资产或先改文档。

```text

B 终点邻域 alpha：均值 255.0 / 标准差 0.0
逐像素完全相同：4/289 = 1%
```

**为什么这是"无结论"而不是"结论"** ✗：两笔的 alpha **完全饱和**（255、标准差 0）=>
**没有可见颗粒**可比较 ✓。也就是说我这个观测量是**平的**：
`texture: 1.0` 在这套介质/参数下**没有**产生纹理起伏（或者它影响的是**颜色**而不是 alpha）。

**下次该改的观测量（写下来，免得重来）**：
1. 换到"**颗粒可见**"的参数组合 —— 例如把 `load`/`wetness` 压低（介质干了才会有颗粒感），
   或者换 `oil`/`pencil` 那些**本来就有颗粒**的介质；
2. 量**颜色通道**（`r/g/b`）而不只是 `alpha`（颗粒很可能体现在浓度/颜色上）；
3. 用一个"**整条笔迹**的纹理剖面"（沿笔迹取一列，看斑点位置）而不是只看终点邻域 ——
   终点的 dab 可能正好被后一笔盖住；
4. 仍然用"**同终点、不同路径**"这个设计 ✓（它能直接区分"画布锚定"与"笔触锚定"）——
   设计没错，错的是**观测量**。

**在拿到可信结论之前，不要动产品代码、也不要改需求文档** ✗（本会话已有三次"拿一个数字当结论"

## 六、第 254 轮：机制查清了（`seed`），但**探针无法隔离**，改动已撤回

### 6.1 机制（读代码得到的确定结论）

* 介质路径在**我们自己的 crate** 里：`crates/yanshi-medium-host/src/lib.rs` 的
  `paint_stroke_over`；每枚 dab 的**纹理种子**原来取自**笔触内序号**：
  ```rust
  let mut counter: u32 = 0;
  counter = counter.wrapping_add(1);
  let seed = counter.wrapping_mul(0x9E37_79B1) ^ 0x5BF0_3635;   // <-- 笔触锚定
  ```
* 插件 ABI（`dab(medium, seed, size, pressure_milli, input)`）**只收 seed/size/pressure**，
  **没有画布坐标** ✗ => 颗粒完全由 `seed` 决定（在插件内部展开）。
* **所以**"画布锚定"的正确做法**不是**改插件 ABI ✗，而是**把 seed 改成画布坐标的整数哈希** ✓
  （纯整数 ⇒ 符合"内核两端同源" ✓）。我在这一轮**确实改了**（`canvas_seed(medium_id, x, y, size)`），
  编译通过、介质判据仍绿。

### 6.2 但**验证不成立** => 改动已**撤回**

用第五节那个"同终点、不同路径"的探针复测（改后）：
```text
watercolor：同路径差 0.00 ／ 不同路径差 7.26   （改前 7.43）
pencil    ：同路径差 0.00 ／ 不同路径差 11.80   （改前 11.56）
```
**差异几乎没变** ✗。原因不是改动无效，而是**探针无法隔离"某点的颗粒"** ✗：
我取的 17×17 窗口里**混进了两条路径各自的早期 dab** —— 那些像素本来就落在**不同位置**上，
所以不管纹理怎么锚定，两幅图在那里都不同 ✓。

**要真验证"某点的颗粒"**，必须先能**只画一枚 dab**（或先把路径的历史擦掉）——
例如给介质路径加一个"单 dab"测试入口，或者用 Rust 单测直接验 `canvas_seed` 的**性质**
（同一坐标 ⇒ 同一种子；不同坐标 ⇒ 大概率不同 ✓），再用一张**只含终点那一枚 dab**的小图做端到端比对。
