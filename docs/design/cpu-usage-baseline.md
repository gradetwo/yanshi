# CPU 用量基线（阶段一第 5 条）

**目的**：为**阶段二（引入 GPU）**留下**可比的前后数**。
**∴ 不许**只留墙钟 ✗ —— **∴ 因为** GPU 的收益有**两本账** ✗：
**① 时间账**（墙钟 ＋ 端到端延迟）✗ ＋ **② CPU 占用账**（进程 CPU ＋ 占比＋ TaskDuration）✓。

## 环境

| 项 | 值 |
|---|---|
| CPU | Intel(R) Core(TM) i5-4250U CPU @ 1.30GHz |
| 核数 | 4 |
| 内存 | 3847 MiB |
| 二进制 | `target/release/yanshi-serve`，mtime `2026-10-10 12:12:50` |
| 量法 | `node scripts/tool-render-cost-accounts.mjs --spawn` |

## 基线（release，4K 整幅，中位数；第一轮为预热已剔除）

| 配置 | 后端 | **① 墙钟 ms** | **② 进程 CPU ms**（utime+stime） | **③ CPU÷墙钟** | **④ 峰值 RSS MB** |
|---|---|---|---|---|---|
| 默认 | cpu（`--gpu auto`） | **3597.2** | **5230.0** | **1.47×** | **2036** |

**读法**：
- **② 是**进程 CPU 时间**✗**（`/proc/<pid>/stat` 的 utime+stime，时钟节拍换算）✓
- **③ 是**并行度代理**✗** —— `1.47×` 意思是**平均用了 1.47 个核** ✓
- **④ 是**峰值常驻**✗**（`VmHWM`）✓ —— **∴ 不是**当前 RSS ✓
- **∴ 第一轮**是**预热**✗ ⇒ **∴ 已**从统计里剔除 ✓（预热墙钟 3233.5 ms）

## 与目标里那条基线的差异（**如实**）

目标记录的是 **2.58 s（墙钟 2.369 s）**；本次实测 **3597.2 ms**。
**∴ 差异约 +52%** ✗ ⇒ **∴ 可能**来自 ✗：
1. **本机当前负载**（同机还跑着别的构建／判据）✓
2. **我这一轮往查看器里加的诊断标记**（每步一个 `push`，**成本很小但非零**）✓
**∴ 两者**都**没有**单独量过** ✗ ⇒ **∴ 所以**：**不要**把这两组数**当成"变慢了 52%"** ✓。

## 判据的诚实性（**它是怎么报的**）

本机**没有 GPU** ⇒ 所有配置都落在 **cpu** 上。
**∴ 表**仍然**立好了** ✗ ⇒ **∴ 一旦**有 GPU ✗，**同一条命令**会**自动**出**两行** ✓。
**∴ 它**没有**因为"只有一行"而报失败** ✗ —— **∴ 那**是对的 ✓（**∴ 一行**也是**合法结果** ✓）。

## 用法（**阶段二的对照**）

上 GPU 之后，**同一条命令**再跑一次，逐项对比本表的四个数。
**∴ 若**只有 ① 变好**而** ②③ 没降（**或更差**）✗ ⇒ **∴ 必须**在汇报里**明说** ✓（**∴ 不许**只报好看的那本 ✗）。

## 附：部分复用三数（阶段一第 1 项）的**不变量**

**不变量**：`below_tiles_available + below_tiles_missing == below_tiles_wanted`
**∴ 为什么必然成立**：实现**对每个想要的格** ✗ ⇒ **∴ 恰好**给 `available` **或** `missing` **加一** ✓。

**守住它的是两处**：
1. `crates/yanshi-render/tests/below_partial_reuse.rs`（**第 180 轮**新增）—— **单带小场景** ✓
2. `scripts/tool-partial-reuse-benefit.mjs`（**第 24 轮**已有）—— **端到端** ✓

**实测**：`measured=true wanted=4 available=2 reused=2` ⇒ **2+2=4** ✓。
**变异检验**：把 `missing` 强制报 0 ⇒ 断言**当场红** ✓（**判据有牙** ✓）。

# 附二：首帧的**阶段分解**（阶段一第 2 条 —— 成本调查）

## 探针（**已存在，不用新增代码**）

**∴ wasm32 上它**是空操作** ✗** —— **∴ 因为** `Instant::now()` 在 `wasm32-unknown-unknown` 上会 panic ✓

**场景**：4K（4096²）＋ 4 层 ＋ 每层一笔（半径 180，`#c8285a`）；**第二次**渲染（第一次是热身）。

## 「量化」这一段含什么（**读码所得**）

`quantize_to_rgba8` 做**两件事**（[render.rs:1038-1046](crates/yanshi-render/src/render.rs) 的注释 ＋ 代码）：

1. **f32 → f16 → f32 往返** ✗
   **∴ 为什么 ✗**：**整幅渲染**与**按 tile 组合渲染**必须**逐字节一致** ✓
   ⇒ **∴ 否则** f32 scratch 与 f16 tile 的舍入差会**出现 ±1 分歧** ✓
   ⇒ **★ 所以**：**这是**正确性的代价**✗，**不是**浪费 ✓ ★
2. **f32 → u8（显示空间）＋ 写 `rgba8` 缓冲** ✓

**∴ 注释自述**：「**4K 上实测约半秒**」✓ ⇒ **∴ 与本次 945.6 ms**同量级 ✓。

## 对决策 ① 的意义（**下一步要测什么**）

**∴ 还没测的那一项**：**第 1 件（f16 往返）与第 2 件（u8 转换）各占多少** ✗。
**⇒ 在 `quantize_to_rgba8` **内部**再加两个计时点即可** ✓（**纯观测，零行为变化** ✓）。
**∴ 若** f16 往返占大头 ⇒ **∴ SIMD** 有明确收益 ✓；
**∴ 若** u8 转换占大头 ⇒ **∴ `wide` **帮不上** ✗ ⇒ **∴ 该查**写缓冲的内存带宽 ✓（**它**与「裁剪+存 tile 20%」**同类** ✓）。
