# 设计：把「首次预览／缩略图生成」推迟到响应之后

## 一、问题（**已实测 ✓**）

**4K 文档首次 `get_document` ⇒ 1079 ms ✗**（其后 0.9 ms ✓，`first_preview_ms` 已如实报出 ✓）。
**归因（**已定位到函数 ✓**）**：`Document::render_document_preview`
⇒ **∴ 那 1079 ms 几乎全是**整幅渲染**✗**（`document.rs:1382` ✓）——
**编码只编 256²（**几 ms ✓**）、存 blob 也很小（**几百 µs ✓**）**。
**∴ 且**该路径已是**增量 ＋ 脏块（第 1040 轮 ✓）**，比旧实现（**1.5–4.0 s ✗**）**快 1.4–3.7× ✓**。
**∴ 所以**缓存路径**已用尽 ✓**（**整幅渲染已走 below ✓，见第 579 轮验收 ✓**）——
**∴ 冷启动第一次**没有任何东西可复用 ✗ ⇒ **∴ 只能改变**"何时算"✗**。

## 二、方案：**推迟（defer）**，不降精度 ✓

**四步（**都在服务端 ✓**）**：

| # | 步骤 | 关键点 |
|---|---|---|
| **①** | **`get_document` 发现缩略图缺失 ⇒ **立刻返回**** | **`first_preview=true` ✓｜`thumb_url=null` ✓｜`preview_state="pending"` ✓**（**显式说明"稍后就绪"✗，不许静默缺图 ✗**） |
| **②** | **把该文档入队**（**同一文档只入一次 ✓**） | **`pending_previews: BTreeSet<DocId>` ✓** |
| **③** | **串行生成**（**一次一个 ✓**） | **复用现有单线程路径 ✓ ⇒ **∴ 无并发风险 ✓**** |
| **④** | **完成后**推送 ＋ 落盘 | **已有 `broadcaster.publish_thumbnail(ThumbKind::Doc256)` ✓** ⇒ **∴ 前端收到后重取 ✓** |

**∴ 预期** ✓：**首次 `get_document` 从 **1079 ms → < 50 ms** ✓**（**只剩队列入队的开销 ✓**）。

## 三、代价（**两面 ✓**，目标第 9 条明文）

| 面 | 内容 |
|---|---|
| **收益** ✓ | **首次读从 ≈1.07 s 降到 < 50 ms ✓**（**≈20× ✓**）｜**交互不再被一次性成本阻塞 ✓** |
| **代价** ✗ | **① 首屏会**短暂没有缩略图**✗**（**从"等 1.07 s 才有"变成"立刻有界面、缩略图随后出现"✓**）｜**② 需要**队列 ＋ 生命周期管理**✗**（**如文档在生成前被关闭 ⇒ 要能取消 / 丢弃 ✓**）｜**③ 多一份**待办状态**✗**（**要能被观测 ✓**） |

## 四、必须守住的约束（**否则会"快而撒谎" ✗**）

1. **不许静默缺图** ✗ ⇒ **缺图时必须带 `preview_state="pending"` ＋ 可读原因 ✓**。
2. **`first_preview` / `first_preview_ms` 必须如实** ✓ ⇒ **推迟后首次应为 `true` / ≈0 ✓**
   （**∴ 若仍报 1079 ⇒ **∴ 说明没真推迟 ⇒ **∴ 判据会红 ✓****）。
3. **慢的仍然要算** ✓ ⇒ **推迟不等于不算**（**目标总则明文 ✓**）⇒ **∴ 生成必须在后台**真的发生 ✓**。
4. **不许引入并发风险** ✗ ⇒ **串行执行 ✓，不复用多线程渲染路径 ✓**。

## 五、验收（**每一条都能红 ✓**）

| # | 判据 | 期望 |
|---|---|---|
| **①** | **首次 `get_document` 墙钟** | **< 50 ms** ✓ |
| **②** | **首次 `first_preview_ms`** | **≈ 0** ✓ |
| **③** | **首次 `preview_state`** | **`"pending"`** ✓ |
| **④** | **稍后（**如 1.5 s**）再取** | **`thumb_url` 就绪 ＋ `preview_state="ready"`** ✓ |
| **⑤ 变异** ✗ | **去掉推迟（**恢复同步生成 ✓**）** | **① 回到 > 1000 ms ⇒ **必红 ✓** |

## 六、与其它目标的接口

* **目标第 2 条（懒渲染）** ✓：**推迟只改"何时渲"✗，而**脏区 ＋ 增量**保持 ✓**
  （**∴ 且**推迟后**不再**需要"冷启动整幅 ✗"以外的特殊处理 ✓）。
* **目标第 3 条（懒编码）** ✓：**生成仍按需触发 ✓，且**编码仍在真正需要缩略图时**发生 ✓**。
* **目标第 6 条（懒保存）** ✓：**快照仍带序号 ＋ 格式版本 ✓；**推迟不影响校验 ✗**。

## 七、⚠️ **与既有决策的冲突**（**必须先解决，否则不能实施 ✗**）

`Document::run_pending_jobs`（`document.rs:1893`）的注释**记录过同方向的尝试及其回退**：

> **这里不再无条件重渲染整幅文档预览** ✗（性能专题，第 1037 轮）……
> **回退（第 1038 轮）**：把"job 完成"与"整幅渲染"解耦会破坏两条既有契约 ✗ ——
> ① `heavy_atoms_create_jobs_and_render_completes_them`（`completed == [job_id]`）之所以能通过，
>   正是因为**渲染顺便调了 `complete_render_jobs()`** ✓；
> ② `jobs_ttl_cancel_and_render_watermark` 还要求**渲染水位随提交推进** ✓。
> ⇒ **∴ 正确方向不是"删掉渲染"✗，而是"让这次渲染**只做变更区域**"✓**
>   —— 见 `thumb.rs` 已有的**分块增量**机制（`incremental.dirty_blocks_for(…)` ✓）。

**∴ 本设计的冲突** ✓：**推迟首次生成 ⇒ 会让"提交时不再渲染"✗** ⇒ **∴ 于是**上述两条契约
**会红 ✗** ⇒ **∴ 所以**在实施前必须**先决定**：
* **① `completed` 的语义** ✓：是否接受"作业完成**不再依赖**渲染"（**即改契约 ＋ 改测试 ✓**）；
* **② 渲染水位** ✓：是否接受"水位**不由提交推进**，而由**渲染发生时**推进"（**同样改契约 ✓**）。

**∴ 更稳妥的替代（**已存在 ✓，且不撞契约 ✓**）** ✓：
**沿用"让渲染只做变更区域"✗**（**第 1038 轮已指明的方向 ✓**），
**∴ 即**把 `render_document_preview` 的**分块增量**（`thumb.rs` 的 `incremental.dirty_blocks_for` ✓）
**覆盖到"冷启动首帧之外"的全部调用 ✓** ⇒ **∴ 于是**：
* **∴ 提交时的整幅渲染**变成**只渲变更块 ✓**（**目标第 8 条里"`raster` 恒定 34.5 ms"就是它的成果 ✓**）；
* **∴ 而冷启动首帧**仍然要整幅 ✓（**∴ 无变更可依 ✓**）—— **∴ 这一份成本**只能靠
  **推迟**（**撞契约 ✗**）或**降精度**（**需两面 ✗**）解决 ✓。

**∴ 结论** ✓：**本设计的四步实现必须先做"契约变更"✗，或**退回**到"接受冷启动首帧的 1.07 s"✓** ——
**∴ 这是一个**需要决策的分叉 ✗**，**∴ 不应在未决策的情况下改代码 ✓**。

## 八、✅ **冲突可以避免**（**本轮澄清 ✓**）—— 只需动**读路径**，不动作业收尾

**我第七节的担心是**多余的 ✗**：**它假设"推迟"必须**改 `run_pending_jobs` ✗**。
**∴ 而实际上** ✓：**两条契约依赖的是**提交收尾**（`run_pending_jobs`）里的渲染 ✓** ——
**∴ 那一行（`document.rs:1925`）**原样保留 ✓** ⇒ **∴ 契约**完全不动 ✓****。

**∴ 真正要改的只是**读路径**（`ensure_document_thumbnail` 的**首次**分支 ✓）**：

| 现状（`service.rs:2741-2770`） | 改为 |
|---|---|
| `if 已最新 { return Ok(Some(url)); }` | **不变 ✓** |
| `if size == Skip { return Ok(None); }` | **不变 ✓** |
| **`let preview = document.render_document_preview()?;`（`:2762`）** | **首次 ⇒ **标记待办 ＋ 返回"pending"信号**✗**（**不渲染 ✓**） |
| `return Ok(Some(preview.url));` | **就绪 ⇒ 返回 `Some(url)`；未就绪 ⇒ `None` ＋ `preview_state="pending"`** ✓ |

**∴ 于是** ✓：
* **① 首次 `get_document`** ⇒ **不渲染 ⇒ **< 50 ms ✓****；
* **② 而预览**会在**下一次提交收尾**（`run_pending_jobs` ⇒ `:1925` ✓）**就绪 ✓**
  （**∴ 而任何编辑都会触发提交 ⇒ **∴ 用户几乎立刻就能看到缩略图 ✓**）；
* **③ 两条契约**完全不受影响 ✓**（**∴ `completed == [job_id]` ✓；渲染水位仍随提交推进 ✓**）；
* **④ 显式同步路径**（**如导出 ✓**）**仍可**要求立即生成**✓**（**如 `preview_state="sync"` 或沿用现有调用 ✓**）。

**∴ 结论** ✓：**本设计**不需要契约变更 ✗** ⇒ **∴ 可以实施 ✓** ——
**∴ 顺序** ✓：**① `preview_state` 字段 ⇒ ② 首次不渲染 ＋ 标记待办 ⇒ ③ 响应携带 pending ⇒ ④ 验收（**首次 < 50 ms；提交后就绪 ✓**）＋ 变异（**恢复同步 ⇒ 首次回到 >1000 ms ⇒ 必红 ✓**）**。
