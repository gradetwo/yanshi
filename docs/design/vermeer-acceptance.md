## 二、不像的原因（**分清"引擎缺"与"编排差"**）

| 现象 | 归因 | 证据 |
|---|---|---|
| 眼形是**多边形** | **编排差** ✓ | `medium_stroke`／`brush_stroke` 都**有 `smooth` 参数**（`medium_stroke` 的可用参数里列着 ✓），而脚本**没用**；控制点也只给了 7 个 ✗ |
| 虹膜是**小点** | **编排差** ✓ | 脚本用 2 个相距 0.04×边长 的点去画"虹膜" ⇒ 那本来就只是一小笔 ✓ |
| 珍珠没有**亮到暗的球感** | **编排差 ＋ 一个真缺口** ✓ | 脚本想用介质路径的 `color_to` 渐变，但介质**不支持** `color_mixing`（见下）✓ |
| 没有任何"形状辅助" | **不是缺口** ✓ | 架构原则就是「**引擎做物理、MCP 做编排**」⇒ 椭圆/球体的控制在**调用方**（AI）手里 ✓ |

## 六、★ `pigment` 分支：根因**已被日志证明**（第 254 轮续） ★

第五节说"唯一还没观测的一环是在服务端打印 `mixing.name()` 与两次 `mix_colors` 的返回值"。
本轮做了（临时探针 `YANSHI_MIX_PROBE=1` ✓），**一次就定位**：

```text
MIX_PROBE medium_point_colors: mixing=pigment points=2
MIX_PROBE index=0 from=[255,255,0] to=[0,0,255] pigment_path=[255,255,0] rgb=[255,255,0] same=true
MIX_PROBE index=1 from=[255,255,0] to=[0,0,255] pigment_path=[0,0,255]   rgb=[0,0,255]   same=true
```

**根因（确证，不再是假设）**：
1. **模式是对的** ✓：`mixing=pigment` 确实传到了 `medium_point_colors` ⇒ 接线没问题 ✓；
2. **但只有 2 个点**（`points=2`）⇒ 只算了 `t=0` 与 `t=1` 两处，
   **而端点处的混色恒等于原色**（不论什么模式 ✓）⇒ 两次结果与 `rgb` **完全相同** ✓；
3. **中段的颜色是 `yanshi-medium-host` 自己的线性插值** ✗（我在 host 里"与路径同步展开颜色"那一步做的就是
   `c0 + (c1-c0)*t` ✓）⇒ **光谱混色在中段根本没参与** ✗ ⇒ 两种模式的中段一模一样 ✓。

**修法（已设计好，下一轮照做）**：**server 先把路径加密，再对加密后的每一点混色** ✓ ——
* 加密点都落在**原线段上** ⇒ **几何不变** ✓（dab 序列基本不变 ✓）；`smooth` 情形下加密发生在**重采样之后** ✓；
* 每一点的混色比例用**整笔的累计比例**（`index` ＋ 段内 `t`）✓；
* 只在**给了 `color_to`** 时才加密与混色 ⇒ 默认与"只给 color"的路径**逐字节不变** ✓。
* **注意**：加密必须**同时**改 `points` 与每点颜色（上一轮我只改了颜色、没改 `points` ⇒
  host 展开后下标越界 ⇒ 那是更早一次的红 ✓）。
